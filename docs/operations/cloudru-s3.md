# Подключение Cloud.ru Object Storage

## Подготовка бакета

Создайте отдельный приватный бакет для фотографий «Тарелки».
Версионирование должно никогда не включаться. Состояние Suspended сохраняет старые версии
и также блокирует удаление в приложении. Перед каждым DELETE приложение проверяет это через
GetBucketVersioning. Ошибка проверки оставляет удаление на повторный прогон.

Выдайте отдельному runtime-ключу права s3:ListBucket и s3:GetBucketVersioning на бакет,
а также s3:GetObject, s3:PutObject и s3:DeleteObject на его объекты.
HeadBucket использует ListBucket, HeadObject — GetObject.
Настройте приватность, проверьте отказ анонимного GET и доступ с ключом приложения.
Вызовы браузера идут через API, подписанные S3-ссылки читает сервер.

## Окружение

Скопируйте .env.example в .env и заполните настройки приложения, БД, Telegram и платежей.
Для Cloud.ru задайте следующие параметры по образцу clipmkr.

```dotenv
S3_ENDPOINT=https://s3.cloud.ru
S3_REGION=ru-central-1
S3_FORCE_PATH_STYLE=false
S3_BUCKET=<имя-своего-бакета>
S3_ACCESS_KEY=<tenant_id>:<key_id>
S3_SECRET_KEY=<Key-Secret>
```

Для S3 требуется отдельный Object Storage ключ. Значения endpoint и региона уточняются
для выбранного сервиса Cloud.ru. Имя бакета при адресации через поддомен должно подходить
для DNS и HTTPS сертификата провайдера. Храните .env с правами 600.

API и recognizer читают все шесть параметров явно. Пустое значение отклоняется при старте.
Cloud.ru бакет создаётся до запуска приложения. ensureBucket выполняет HeadBucket.
Миграции PostgreSQL и импорт USDA выполняются по существующей инструкции развёртывания.

```bash
docker compose --profile edge config -q
docker compose --profile edge build
docker compose up -d --wait db
# После миграций и импорта справочника
docker compose --profile edge up -d
```

Для profile edge на хосте требуется существующая внешняя сеть talk-ai-public и настроенный
вышестоящий reverse proxy. Единственный опубликованный порт — 127.0.0.1:N4_EDGE_PORT.

## Перенос существующих фотографий

1. Сохраните защищённую резервную копию БД и параметры исходного MinIO.
   Определите источник по прежнему окружению работающего приложения.
2. Скопируйте в новый бакет все оригиналы, normalized-копии и share-cards,
   сохраняя исходные object key и Content-Type. Используйте инструмент с отдельными
   профилями доступа к источнику и назначению, например rclone.
   Сначала выполните dry-run и проверьте направления. Выполните copy, затем check
   с download для побайтового сравнения. ETag провайдера может отличаться от хэша данных.
3. Сверьте список объектов и ключи из photo.object_key, photo.normalized_object_key
   и share_card.object_key с новым бакетом.
4. На финальное окно переключения остановите API и recognizer, включая фоновые уборщики.
   Повторите копирование и сверку относительно актуального исходного бакета.
   Отдельно сопоставьте удаления, произошедшие после первого копирования.
   Удаляйте лишние целевые копии только по проверенному списку для выделенного бакета.
5. Задайте S3_* для обоих процессов, запустите их и проверьте прежние фотографии,
   нормализованные изображения и карточки. Затем выполните путь с синтетической фотографией
   от загрузки до просмотра и удаления. Анонимный GET объекта должен возвращать отказ.
6. Зафиксируйте момент переключения, количество объектов и результаты проверки байтов.
   Сохраните исходный бакет с ограниченным доступом на согласованный срок восстановления.
   Обработайте запросы удаления в защищённых копиях и завершите их хранение по этому сроку.

## Обратное переключение

Остановите запись и фоновые процессы. Сопоставьте новые объекты и удаления после перехода
с исходным бакетом, перенесите актуальные данные с прежними ключами и проверьте байты.
Верните endpoint, регион, forcePathStyle и ключи исходного MinIO одновременно обоим процессам.
Для локального MinIO используются http://storage:9000, us-east-1, true.
Проверьте фотографии и карточки после возобновления работы.

## Локальные тесты

Задайте отдельные N4_STORAGE_ROOT_USER, N4_STORAGE_ROOT_PASSWORD, N4_S3_ACCESS_KEY,
N4_S3_SECRET_KEY, N4_S3_BUCKET. Профиль test всегда использует локальный MinIO,
регион us-east-1 и path-style true. Production S3_* в него не передаются.

```bash
docker compose -p n4-test --profile test up -d --wait db storage storage-init
bash scripts/create-test-database.sh -p n4-test
docker compose -p n4-test --profile test run --rm test npm run test:integration
```

Для локального приложения сначала поднимите storage/storage-init с profile local-storage,
затем укажите локальные endpoint и реквизиты пользователя в S3_* и запустите app.

## Проверки до переключения

Выполните npm test, npm run typecheck, npm run lint, npm run build и check-env-wiring.
Unit-тесты s3-storage.test.ts выполняют реальный AWS SDK на локальном HTTP fixture.
Живой Cloud.ru smoke требует реквизитов целевого бакета и выполняется отдельно.
Для smoke используйте уникальный ключ синтетического фото, проверьте PUT/GET/HEAD,
подписанный GET, совпадение байтов и Content-Type, затем DELETE и отсутствие объекта.
